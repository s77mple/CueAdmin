## 1. 一页结论

**系统 = 五条「通路模板」；开一批货 → 选一个模板 → 系统生成这条批的链路（货流 + 票流 + 质检）→ 用户沿链路按顺序录单（货/质检按序推、票后补）→ 按团队隔离、双方可见。**

| 块 | 内容 | 性质 |
|---|---|---|
| A | 用户/部门/角色/菜单/权限码 | 【现有】配置即用 |
| B | `subjects` 主体档案 + 数据权限（按部门隔离） | 【新增·procurement 应用】 |
| C | `route_templates` 通路模板 + `template_steps` 步骤 + `batches` 批次 | 【新增·procurement 应用】 |
| D | `deals`（采购单）+ 票/款子表 + `quality_tests` 质检 + 附件 | 【新增·procurement 应用】 |
| E | 前端：批次看板 / 批次链路推进 / 交易明细 / 质检 / 主体档案 | 【新增·页面】 |

**落地位置**：后端全部在 `backend/app/procurement/`（新应用），前端在 `frontend/src/api/procurement/` + `frontend/src/views/procurement/`。

**本期明确不做**：自动对账/勾稽引擎、销售台账（我方卖方段经对方采购记录只读可见）、任务流/待办派单（顺序推进只是「按步骤录」，不是流程引擎）、外部供应商自助登录、历史数据回填。

## 2. 核心概念（先读这一节）

### 2.1 四个名词

| 概念 | 是什么 | 例子 |
|---|---|---|
| **通路模板 route_template** | 一条「这张货要走哪几步」的清单：**货流链 + 票流链 + 质检点** | 「干柚果·通路1」 |
| **步骤 step** | 模板里的一步：类型 = 货 / 质检 / 票，带顺序、买方、卖方（或被检主体） | 「第1步 货 果农→GP」 |
| **批次 batch** | 开批时选一个模板，生成这条批的链路（模板的实例化） | P260901 → 选「干柚果·通路1」 |
| **记录 record** | 往某一步里填的实际内容，挂在「步骤 + 批次」上 | 第1步录成的一笔采购单 |

> 关键区别：**模板是「配方」，批次是「照配方开的一单」**。配方只有 5 份，批次可以无数条，每条都指向一份配方。

### 2.2 三种步骤类型（这是整套设计的核心）

| 类型 `step_type` | 中文 | 占推进格？ | 录到哪张表 | 谁录 |
|---|---|---|---|---|
| `goods` | 货（实货购销） | ✅ 占，按顺序 | `deals` | 买方所属团队 |
| `qc` | 质检 | ✅ 占，按顺序 | `quality_tests` | 质检角色（林丽薇） |
| `invoice` | 票（票款层，可无实货） | ❌ 不占，后补 | `deals` | 买方所属团队 |

**主链 = `goods` + `qc` 混合按序排**（货到哪检到哪），`invoice` 是旁支。

> ⚠️ 术语区分：**票流「步骤」**（`invoice` step，录成一笔 `deals` 转开票单）≠ **发票「明细」**（`deal_invoices`，挂某笔 deal 下的发票号/金额/税率）。前者是「开票这道工序」，后者是「这张发票本身」。

### 2.3 货流 vs 票流（为什么是两条链）

**「货去哪」和「钱票怎么走」经常不是一回事**：通路1 里货是「果农直发 GP」，但票要「果农→CNSM→客都文旅→GP」转一圈（转开票 + 内部挂账）。所以：

- **货流** = 实货走的路（`goods` 步骤），顺序物理决定。
- **票流** = 钱/票走的路（`invoice` 步骤），可后补、可无实货（转开票）。
- **质检** = 挂在货流收货/产出节点上的 `qc` 步骤，无金额。

三条线靠**同一个批号**串成一批。

## 3. 五条通路模板（权威数据）

主体缩写：**GP**=金柚康、**GH**=金骏康、**CNSM**=昌农商贸、**立博/百泓源/普兰特/华萃康健**=代工厂。

| # | 模板名 | 货流（实货） | 票流（钱票） |
|---|---|---|---|
| 1 | 干柚果/片 · 通路1 | 果农→GP→立博→CNSM→GP | 果农→CNSM→客都文旅→GP→立博→CNSM→GP |
| 2 | 干柚果/片 · 通路2 | 果农→代工厂(普兰特/华萃康健)→GH→立博→CNSM→GP | 果农→CNSM→GH→代工厂→GH→立博→CNSM→GP |
| 3 | 酸橙/胡柚 | 果农→代工厂(百泓源)→GP | 果农→CNSM→GP |
| 4 | 贸易① 柚苷/异香兰素 | 供应商→GH→立博→CNSM→GP | 供应商→GH→立博→CNSM→GP（货票同路） |
| 5 | 贸易② 新橙皮苷 | 供应商-三叶→GP | 供应商-三叶→CNSM→GP |

> 货流每段的货品：通路1 = 干柚果/片 → 柚苷(自产) → 新橙皮苷 → 新橙皮苷；其余模板的货品在各段 `goods` 字段配。

### 3.1 通路1 完整步骤（含质检点，作为其余模板的参考例）

质检点规则：**每个货流段的「收货」和「产出」节点各挂一个质检步骤**。通路1 主链展开为 8 步：

| 步骤 | 类型 | 内容 | 谁录 |
|---|---|---|---|
| 1 | 货 | 果农 → GP（干柚果/片） | GP 团队 |
| 2 | 质检 | GP 采购检验（干柚果到货） | 林丽薇 |
| 3 | 质检 | GP 生产检验（柚苷自产产出） | 林丽薇 |
| 4 | 货 | GP → 立博（柚苷） | 昌农（立博代管） |
| 5 | 质检 | 立博双检验（收柚苷 + 产新橙皮苷） | 林丽薇 |
| 6 | 货 | 立博 → CNSM（新橙皮苷） | 昌农 |
| 7 | 货 | CNSM → GP（新橙皮苷） | GP 团队 |
| 8 | 质检 | GP 采购检验（新橙皮苷到货） | 林丽薇 |

票流 6 步（旁支，不占推进）：

| 票 | 内容 |
|---|---|
| 票1 | 果农 → CNSM |
| 票2 | CNSM → 客都文旅 |
| 票3 | 客都文旅 → GP |
| 票4 | GP → 立博 |
| 票5 | 立博 → CNSM |
| 票6 | CNSM → GP |

> 其余 4 个模板的质检点按同一规则配置（seed 时录数据），本文以通路1 为完整示范。

## 4. 数据模型（9 张表，全字段 + 外键）

### 4.0 模型写法约定（对齐现有 `app/system/models/`）

- 所有表继承 `Base`（`app.core.storage`）+ `TimestampMixin`（自动带 `created_at`/`updated_at`，DB 层 `server_default`/`server_onupdate` + ORM 层 `onupdate` 双保险）。
- 主键：`id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True, comment="主键")`。
- 每列都带 `comment=`（中文说明），类型用 `String/Numeric/Boolean/DateTime/BigInteger`。
- 外键：`ForeignKey("表名.id", ondelete="...")`，删除策略按语义选（`SET NULL` 保数据 / `CASCADE` 级联）。
- 金额一律 `Numeric(18,2)`、数量 `Numeric(18,3)`；金额只出现在 `deals` 及票/款子表；**`quality_tests` 无任何金额字段**。
- `→` 表示外键指向。

> 下面 9 张表的 `created_at`/`updated_at` 由 `TimestampMixin` 统一提供，不逐表列出；`created_by` 是显式外键列（不是 mixin 字段）。

### 4.1 主体档案 `subjects`

```
id                    主键（BigInteger）
code                  唯一标识，unique（cnsm / gp / gh / libo / ke / farmer …）
name                  主体名称
is_login              是否登录（果农、供应商 = false，不建账号）
owner_department_id   → departments.id   该主体归哪个部门管（数据权限依据）
```

### 4.2 通路模板 `route_templates`

```
id                    主键
name                  模板名，unique（"干柚果·通路1" …）
```

### 4.3 模板步骤 `template_steps`

```
id                    主键
template_id           → route_templates.id     属于哪个模板
seq                   顺序（主链 1,2,3…；票 1,2,3…，见 §5 推进规则）
step_type             类型：goods（货）/ qc（质检）/ invoice（票）
buyer_subject_id      → subjects.id            买方（goods/invoice 用，qc 为空）
seller_subject_id     → subjects.id            卖方（goods/invoice 用，qc 为空）
inspect_subject_id    → subjects.id            被检主体（qc 用，其余为空）
goods                 货品名（goods 用）
stage                 质检环节：采购检验 / 生产检验（qc 用）
product               质检产品（qc 用）
```

### 4.4 批次 `batches`

```
id                    主键
batch_no              批号（P260901），unique
template_id           → route_templates.id     选了哪个模板
created_by            → users.id               开批人
```

> 批次「状态/进度」**不存列**，靠「该批各步骤是否有记录」现算（见 §5.3）。

### 4.5 采购单 `deals`（`goods` 与 `invoice` 步骤都录这里）

```
id                    主键
batch_id              → batches.id             哪一批
step_id               → template_steps.id      填的是模板第几步
buyer_subject_id      → subjects.id            买方（锁定，从步骤来）
seller_subject_id     → subjects.id            卖方（默认步骤值，可换）
goods                 货品
spec                  规格型号
qty                   数量 / KG
price                 含税单价（元/KG）
amount                合同金额（= qty × price，自动）
contract_no           合同编号
contract_date         采购日期
status                单据状态：进行中 / 待收货 / 已结算
recv_date             收货日期
recv_qty              收货数量 / KG
recv_addr             收货地址
recv_by               收货人
goods_condition       货物情况（正常 / 包装破损）
coa_batch_no          COA 批号
logistics_co          物流公司
logistics_no          物流单号 / 车牌号
created_by            → users.id               录入人
```

### 4.6 票子表 `deal_invoices`（0..n，可后补、多张）

```
id                    主键
deal_id               → deals.id               属于哪笔采购单（ondelete=CASCADE）
inv_date              发票日期
inv_no                发票号码
inv_type              发票类型（增值税专用 / 增值税普通）
tax_rate              税率 %
inv_amt               发票金额
credit_days           账期 / 天
```

### 4.7 款子表 `deal_payments`（0..n，分次付款）

```
id                    主键
deal_id               → deals.id               属于哪笔采购单（ondelete=CASCADE）
pay_date              付款日期
paid_amt              已付款金额
```

> **未付款金额 = `deals.amount` − Σ `deal_payments.paid_amt`**，现算不存。

### 4.8 质检记录 `quality_tests`（`qc` 步骤录这里）

```
id                    主键
batch_id              → batches.id             哪一批
step_id               → template_steps.id      填的是模板第几步（质检步骤）
subject_id            → subjects.id            被检主体
stage                 环节：采购检验 / 生产检验
product               产品
result                含量结果（含量 % / 水分 / 复测等）
date                  检测日期
inspector_id          → users.id               检测人（林丽薇）
```

### 4.9 附件 `attachments`（挂采购单或质检记录下）

```
id                    主键
deal_id               → deals.id               挂在哪笔采购单下（合同/磅单/发票用；与 quality_test_id 二选一，ondelete=CASCADE）
quality_test_id       → quality_tests.id       挂在哪条质检记录下（检测报告用；与 deal_id 二选一，ondelete=CASCADE）
kind                  类型：合同 / 磅单 / 发票 / 检测报告
file_name             文件名
oss_url               OSS 地址（文件本体在 OSS，表里只存 URL）
```

> `deal_id` 与 `quality_test_id` **恰一个非空**（应用层校验）：合同/磅单/发票挂采购单，检测报告挂质检。

### 4.10 外键汇总（表怎么连）

```
route_templates.id  ←  template_steps.template_id
route_templates.id  ←  batches.template_id
template_steps.id   ←  deals.step_id
template_steps.id   ←  quality_tests.step_id
batches.id          ←  deals.batch_id
batches.id          ←  quality_tests.batch_id
deals.id            ←  deal_invoices.deal_id
deals.id            ←  deal_payments.deal_id
deals.id            ←  attachments.deal_id
quality_tests.id    ←  attachments.quality_test_id
subjects.id         ←  template_steps.buyer/seller/inspect_subject_id
subjects.id         ←  deals.buyer/seller_subject_id
subjects.id         ←  quality_tests.subject_id
departments.id      ←  subjects.owner_department_id
```

**三条决定性的线**：`batches.template_id`（批次选模板）、`deals.step_id` / `quality_tests.step_id`（记录对哪步）、`deals.batch_id` / `quality_tests.batch_id`（记录属哪批）。

> 跨应用外键说明：`subjects.owner_department_id → departments.id`、`deals.created_by → users.id`、`quality_tests.inspector_id → users.id` 指向的是 **system 应用**的 `departments`/`users` 表。procurement 不复制这两张表，直接建外键引用（同库跨应用共享，与现有 `user_roles` 等关联表同库同源）。

## 5. 录入与推进规则

### 5.1 开批

建批次 → 选模板 → 系统按 `template_steps` 把这条批的链路列出来（货+质检按 `seq` 排，票挂旁支）。

### 5.2 顺序推进（只对主链）

- 主链（`goods` + `qc`）按 `seq` **硬锁顺序**：只有「第一个没有记录的步骤」显示「录入」按钮，录完推进到下一步。
- 「某步录没录」= 查该步骤有没有记录：`goods`/`invoice` 查 `deals.step_id`，`qc` 查 `quality_tests.step_id`。
- 一个 `qc` 步骤可挂**多条**质检记录（如通路1 第5步双检验 = 2 条），只要 ≥1 条即视为「已录」。

### 5.3 当前步骤（进度）的计算

```
主链 = step_type ∈ {goods, qc} 的步骤，按 seq 排序（票的 seq 从 1 另起，不与主链混排）
取主链第一个「无记录」的步骤 = 当前步骤
批次进度 = 已录主链步骤数 / 主链步骤总数
批次闭环 = 全部主链步骤已录 且 全部票步骤已录
```

### 5.4 票后补（不占推进）

- 票步骤**不参与**「当前步骤」计算。
- 唯一门槛：**第一笔 `goods` 步骤录完，票才开放**（没采购哪来票）。
- 开放后票可随时录、不限先后、可后补；系统只看「票是否录齐」（齐 = 闭环条件之一）。

### 5.5 谁录（写权限）

- `goods` / `invoice` 步骤：**买方主体所属部门**的团队录（无账号上游由代管方代录）。
- `qc` 步骤：**质检角色**（林丽薇）录。
- 后端写前校验：录 `goods`/`invoice` 时 `buyer_subject_id` 必须在本用户范围；录 `qc` 时要求质检角色。

## 6. 数据权限

**核心：数据权限不建权限表、不加 data_scope 列，靠「主体挂部门 + 用户挂部门 + 查询时过滤」。**

### 6.1 三个组成

1. **主体挂部门**：`subjects.owner_department_id`（CNSM/客都文旅/立博 → 昌农部门；GP/GH → GP-GH 部门）。
2. **人挂部门**：`users.department_id`（现有 system 应用字段）。
3. **查询时过滤**：每次查数据，先算「我管的主体集合」，再过滤。

### 6.2 可见性（读）

一条 `deals` 记录，用户可见当且仅当：

```
用户是 admin（全部可见）
或 buyer_subject_id ∈ 我的主体范围
或 seller_subject_id ∈ 我的主体范围
```

「我的主体范围」= `SELECT id FROM subjects WHERE owner_department_id = 我的部门id`（由 `GET /api/v1/procurement/my-subjects` 提供，前端据此渲染「能录哪些段/能看到哪些记录」）。

`quality_tests` 同理：`subject_id ∈ 我的范围` 或质检角色（质检角色对质检记录全部可见，因质检无金额、跨团队共享）。

### 6.3 可写（录/改/删）

- `deals`：**买方在我范围**才可建/改/删（卖方侧只读）。→ 我方既是买方又是卖方的段，买方可改、卖方只读。
- 数据范围外操作 → `BusinessException(ErrorCode.DEAL_OUT_OF_SCOPE, "该交易/抬头不在你的数据范围内")`。
- 权限码不足（如没有 `deal:update`）→ 框架 `Security(scopes=[...])` 自动拒绝，返回 `ACCESS_DENIED`（16001）。

### 6.4 举例

陈雄珍（昌农部门，范围 = CNSM/客都文旅/立博）：
- 段6「立博→CNSM」他是买方 → 能看能改。
- 段7「CNSM→GP」他是卖方 → 只能看（GP 录的）、只读。
- GP 当买卖双方的段（如段4「GP→立博」买方立博=昌农代管，卖方 GP）→ 昌农（代管买方）能录，GP 只读可见。

## 7. 采购单字段规格（统一一套，贸易/代工不区分）

> v2 起**删除 `template_type`（贸易类/代工类）**——「这段是贸易还是代工」由模板步骤本身表达（代工厂 = 卖方主体），不再单列字段。

### 7.1 `deals` 主档字段（= 合同 + 收货）

- **合同**：采购方(买方主体)、供应商(卖方主体)、采购日期、合同编号、货物名称、规格型号、数量/KG、含税单价、合同金额(自动)、单据状态。
- **货/收货**：收货日期、收货数量、收货地址、收货人、货物情况、COA 批号、物流公司、物流单号/车牌号。

### 7.2 票 `deal_invoices`（0..n）

发票日期、发票号码、发票类型、税率%、发票金额、账期/天。

### 7.3 款 `deal_payments`（0..n）

付款日期、已付款金额。未付款 = 合同金额 − Σ已付（自动）。

### 7.4 质检 `quality_tests`（无金额）

环节(采购/生产检验)、被检主体、产品、含量/水分/复测结果、检测日期；检测报告（附件，走 `attachments.quality_test_id`）。

### 8.4 接口清单（前缀统一 `/api/v1/procurement/`）

| 资源 | 方法 + 路径 | 说明 |
|---|---|---|
| 主体 | `GET /subjects`、`POST /subjects`、`PUT /subjects/{id}`、`DELETE /subjects/{id}` | admin 维护 |
| 我的主体 | `GET /my-subjects` | 返回当前用户可见主体集合（仅认证不鉴权，同 `/routes`） |

| 采购单 | `GET /deals`、`POST /deals`、`PUT /deals/{id}`、`PATCH /deals/{id}`、`GET /deals/{id}`、`DELETE /deals/{id}` | list 含双方可见 SQL + 批号/步骤筛选 |
| 采购单子记录 | `POST/GET/DELETE /deals/{id}/invoices`、`POST/GET/DELETE /deals/{id}/payments` | 票/款子表 |
| 质检 | `GET /quality`、`POST /quality`、`PUT /quality/{id}`、`PATCH /quality/{id}`、`GET /quality/{id}`、`DELETE /quality/{id}` | 按 环节/被检主体/批号 筛选 |
| 附件 | `POST /attachments`(传 OSS)、`GET /attachments`、`PUT /attachments/{id}`、`DELETE /attachments/{id}` | 文件本体走 OSS；上传时 `deal_id` / `quality_test_id` 二选一（合同/磅单/发票挂采购单，检测报告挂质检）；update = 改元数据或重传 |

**响应契约**（沿用现有约定，不另起炉灶）：
- 统一 `ApiResponse(code, message, data)`，`ok()`/`fail()`；分页 `PageData(items, total, page, page_size, has_more)` + `paginate(session, stmt, page, page_size)`。
- 每个接口 `response_model=ApiResponse[XxxRead/XxxItem/...]` **不可省**。
- Schema 命名：请求 `XxxCreate/XxxUpdate/XxxPatch`（Pydantic，**无** `from_attributes`）；响应 `XxxRead`（回显）/ `XxxListItem`（列表行）/ `XxxBrief`（下拉/嵌套）；响应体 `model_config = {"from_attributes": True}`，**响应字段一律不加 `= None`/`default_factory`**（OpenAPI 里全部必返，可空用 `str | None` 表达）。
- 写接口在 **Service 层**做 §5（推进锁 + 票后补）与 §6（数据范围）校验，`commit`/`rollback`/`IntegrityError` 翻译也留在 Service；**Repository 只做查/存，不 commit、不抛业务异常**。

## 12. 验收标准

1. **开批**：新建批次选「干柚果·通路1」→ 系统列出 8 主链 + 6 票。
2. **顺序推进**：只开放当前步骤；录完第1步（果农→GP）自动推进到第2步；跳过第2步直接录第4步被拒（`DEAL_STEP_LOCKED`）。
3. **票后补**：第1步录完票才开放；票可任意先后录、可后补；主链走完但票未齐 → 显示「未闭环」。
4. **谁录**：货步骤只能买方团队录（段4 买方立博 = 昌农代录，GP 不能录）；质检步骤只有林丽薇能录（`QUALITY_PERMISSION_DENIED`）。
5. **双方可见**：段7「CNSM→GP」GP 录、昌农只读可见；段6「立博→CNSM」昌农录、GP 看不到（GP 不在买卖双方）。
6. **数据隔离**：昌农人建不了「买方=GP」的记录（`DEAL_OUT_OF_SCOPE`）；陈总（admin）全部可见。
7. **质检无金额**：质检记录页/接口无任何金额字段。

## 13. 决策记录（最终锁定）

| # | 决策 |
|---|---|
| D1 | 每笔交易 = 一条共享记录，不搞「双方各自录再勾稽」 |
| D2 | 录「买方属于我方体系」的采购；卖方不建销售台账，卖方团队经对方采购记录只读可见 |
| D3 | 主档 + 票(0..n) + 款(0..n)；未付款 = 合同金额 − Σ已付 自动算 |
| D4 | **模板制**：5 条通路模板，开批选模板实例化链路（取代旧「批号只是字段」） |
| D5 | **删除 `template_type`（贸易/代工）**，段性质由模板步骤表达 |
| D6 | 质检是链里**独立步骤**（占推进格），挂 `quality_tests`，无金额 |
| D7 | 主链（货+质检）**硬锁按序推进**；票**后补**（第一笔货录完开放、不限顺序） |
| D8 | 数据权限 = `subjects.owner_department_id` + `users.department_id` + 查询过滤；**不建权限表、不加 role.data_scope 列** |
| D9 | 外部主体（果农/供应商）不登录，由代管方代录 |
| D10 | 附件走 OSS：文件存 OSS，表里只存 URL |
| D11 | 不做任务流/待办/状态机；「顺序推进」是「按步骤录」，不是流程引擎 |
| D12 | 通路1 作为**独立应用 `app/procurement/`**（与 `app/system/` 平级），不塞进 system；`BaseRepository` 上提到 `app/core/repository.py` 供两应用共用 |

## 14. 工作约定（对齐现有代码）

- **建表/迁移**：开发环境 `python seed.py`（顶部 `Base.metadata.create_all` 一键建表 + 幂等灌数据，**无 DROP**）；对**已有表改结构**走 Alembic（`autogenerate` + `upgrade`），不要在 seed 里 drop 重建。
- **错误码**：新码进 `app/core/exceptions.py` 的 `ErrorCode`（IntEnum，`(value, description)`），自动暴露于 `GET /api/v1/system/meta/error-codes`。
- **模型**：`Mapped`/`mapped_column`、BigInteger 主键、每列 `comment=`、`TimestampMixin`（时间戳）、外键 `ondelete`、M2M 用 Core `Table`（procurement 无 M2M，此项备用）。
- **分层**：api（薄控制器，只 `Security`+`response_model`+调 Service）→ service（校验/事务/缓存/`IntegrityError` 翻译）→ repository（查/存，不 commit 不抛业务异常）→ model。
- **响应**：`ApiResponse`/`PageData`/`paginate`；Schema 请求体无 `from_attributes`、响应体 `from_attributes=True` 且字段不加默认值。
- 每个里程碑按 §12 对应项冒烟。
