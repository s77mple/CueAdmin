# CueAdmin 部署手册

前后端分离部署：**前端静态文件放 OSS，后端服务跑在服务器上，两个独立域名。**

---

## 一、架构总览

```
                        ┌────────────────────────────────────┐
浏览器 ── cue-admin.xxx ─┤ DNS: CNAME → ESA 接入地址           │
                        │            ↓                       │
                        │      ESA 边缘节点                   │
                        │      缓存 + 压缩（按主机名匹配）      │
                        │            ↓ 回源                  │
                        │        OSS（前端静态文件）           │
                        └────────────────────────────────────┘

                        ┌────────────────────────────────────┐
浏览器 ── cue-api.xxx ──┤ DNS: A → 服务器公网 IP              │
                        │            ↓                       │
                        │   服务器 nginx :443（SSL 证书）      │
                        │            ↓ TLS 终止              │
                        │   proxy_pass 127.0.0.1:8000        │
                        │            ↓                       │
                        │  FastAPI（gunicorn+uvicorn worker） │
                        │            ↓                       │
                        │    MySQL          Redis            │
                        └────────────────────────────────────┘
```

**两条链路完全独立。** 后端不走 ESA，ESA 上也不需要任何 `/api` 转发规则 —— 因为前端发请求时带的是**完整后端域名**，浏览器直接找 `cue-api.xxx`，不经过前端那个域名。

### 组件清单

| 组件 | 作用 | 管什么 | 不管什么 |
|---|---|---|---|
| **DNS** | 域名 → 地址 | 解析 | — |
| **ESA** | 前端静态资源加速 | 前端缓存/压缩 | **后端完全不管** |
| **OSS** | 存前端构建产物 | 静态文件 | 不执行代码 |
| **服务器 nginx** | 后端 HTTPS + 转发 | TLS 终止、转发到本机 | 不管前端 |
| **gunicorn** | 跑 FastAPI（管进程） | worker 存活、优雅重启 | 不管业务 |
| **uvicorn worker** | 跑 FastAPI（处理请求） | 业务逻辑 | — |
| **MySQL / Redis** | 数据 / 会话缓存 | — | — |

## 二、前置准备

| 项 | 要求 | 备注 |
|---|---|---|
| 域名 | 一个已备案的根域名 | 备案按根域名办，子域名不用重复备案 |
| 备案 | 大陆节点必须 | OSS / ESA / 服务器在大陆都需要，1~3 周 |
| 服务器 | 2C4G 起 | 需装 MySQL 8.0+、Redis 6.0+、Python 3.12+ |
| OSS | 一个 Bucket | 用于放前端构建产物 |
| ESA | 一个站点 | 绑定根域名 |

**子域名规划：**

```
<root>                 ← 已买的根域名，例：example.com
├── cue-admin.<root>   ← 前端（CNAME → ESA）
└── cue-api.<root>     ← 后端（A → 服务器 IP）
```

子域名在 DNS 里免费加，不限数量。

## 三、第一步：后端上线

### 3.1 拉代码、装依赖

```bash
cd /www/wwwroot
git clone <仓库地址> cueadmin
cd cueadmin/backend

# 建议用 venv 隔离（宝塔自带的 Python 版本可能不对）
python3.12 -m venv venv
source venv/bin/activate

pip install -r requirements.txt
```

> **Python 必须 >= 3.12。** 项目用了 `datetime.UTC`、`X | None` 语法糖等特性。
>
> **venv 放哪都行。** 上面用的是项目内的 `venv/`（自包含，好管理）。
> 如果走宝塔「Python 项目管理器」创建，venv 会在 `/www/server/pyporject_evn/<项目名>/`，
> 后面 3.4 的 gunicorn 路径要跟着换成 `/www/server/pyporject_evn/cueadmin/bin/gunicorn`。

### 3.2 配置环境变量

```bash
cp .env.example .env
vim .env
```

| 变量 | 生产环境填什么 |
|---|---|
| `DATABASE_URL` | `mysql+aiomysql://用户:密码@127.0.0.1:3306/cueadmin` |
| `JWT_SECRET` | **换成随机串**，见下方生成命令 |
| `JWT_ALGORITHM` | `HS256` |
| `JWT_ACCESS_EXPIRE_MINUTES` | `15` |
| `JWT_REFRESH_EXPIRE_DAYS` | `7` |
| `REDIS_URL` | `redis://127.0.0.1:6379/0` |
| `APP_ENV` | **`production`** |
| `DEBUG` | **`false`** |

生成随机密钥：

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

> ⚠️ **`DATABASE_URL` 和 `JWT_SECRET` 不填或填默认值，应用会拒绝启动。** 这是 `settings.validate_secrets()` 的硬校验，不是警告。
>
> `JWT_SECRET` 一旦泄露，任何人都能伪造 token 登录任意账号。**不要提交进 git。**

### 3.3 建库 + 建表 + 灌种子数据

```bash
# 建库（utf8mb4 必须）
mysql -u root -p -e "CREATE DATABASE cueadmin CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci"

# 建表 + 种子数据（会创建 admin 账号、24 权限、14 菜单、4 部门、4 岗位）
python seed.py
```

输出末尾会打印默认账号：

```
默认账号: admin / admin123
```

> ⚠️ **首次登录后立刻改密码**（或至少别让 `admin123` 暴露在公网）。

### 3.4 启动服务

**先手动验一次**，确认能起来（前台跑，Ctrl+C 停）：

```bash
# 在 backend/ 目录下执行
/www/wwwroot/cueadmin/backend/venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

看到这样的日志就对了：

```
应用启动完成
Swagger 文档: http://127.0.0.1:8000/docs
...
```

**然后交给进程守护**（宝塔「软件商店 → 进程守护管理器」）。

生产环境用 **gunicorn 管进程 + uvicorn worker 跑异步**，不要直接跑裸 `uvicorn`：

```bash
# gunicorn 不在 requirements.txt 里，单独装
/www/wwwroot/cueadmin/backend/venv/bin/pip install gunicorn
```

宝塔「进程守护管理器 → 添加进程」：

| 项 | 值 |
|---|---|
| 名称 | `cueadmin` |
| 启动命令 | `/www/wwwroot/cueadmin/backend/venv/bin/gunicorn app.main:app -b 127.0.0.1:8000 -w 2 -k uvicorn.workers.UvicornWorker` |
| 运行目录 | `/www/wwwroot/cueadmin/backend` |
| 启动用户 | `root`（或与文件属主一致） |

**命令逐段拆开：**

| 部分 | 作用 |
|---|---|
| `gunicorn` | 进程管理器：worker 崩了自动拉起、支持优雅重启 |
| `app.main:app` | ASGI 应用路径，和 `uvicorn` 开发时一样 |
| `-b 127.0.0.1:8000` | **只监听本机** —— 外网统一走 nginx，8000 端口对外是关的 |
| `-w 2` | 2 个 worker 进程 |
| `-k uvicorn.workers.UvicornWorker` | worker 类型：uvicorn（能处理 async） |

> **`app.main:app` 这个格式和开发时 `uvicorn app.main:app` 完全一致**，所以改起来只是把 `uvicorn --host --port` 换成 `gunicorn -b -w -k`。
>
> 服务器上已有的 FastAPI 项目就是这么跑的，可以直接参考：
> `/www/server/pyporject_evn/developServer/bin/gunicorn app.main:app -b 127.0.0.1:8050 -w 2 -k uvicorn.workers.UvicornWorker`

**⚠️ worker 数量 × 数据库连接池上限，别超过 MySQL 的 `max_connections`**

项目的引擎配置是 `pool_size=10, max_overflow=20`，**单个 worker 最多占 30 条连接**：

| worker 数 | 最多占用连接 |
|---|---|
| `-w 1` | 30 |
| **`-w 2`（推荐）** | **60** |
| `-w 4` | 120 |
| `-w 8` | 240 ← 超过 MySQL 默认的 151 了 |

后台管理系统并发不高，**`-w 2` 足够**。同一台服务器上还跑着别的服务，也要一起算进去。

> **线上绝对不要加 `--reload`**（开发时的热重载，生产环境会拖慢并导致进程异常）。

宝塔的进程守护管理器底层就是 **supervisor**，它生成的配置文件长这样（**不用手写，填完表格自动生成**，这里贴出来是为了让你知道 `directory` 这一项为什么不能填错）：

```ini
[program:cueadmin]
command=/www/wwwroot/cueadmin/backend/venv/bin/gunicorn app.main:app -b 127.0.0.1:8000 -w 2 -k uvicorn.workers.UvicornWorker
directory=/www/wwwroot/cueadmin/backend
autorestart=true
startsecs=3
startretries=3
stdout_logfile=/www/server/panel/plugin/supervisor/log/cueadmin.out.log
stderr_logfile=/www/server/panel/plugin/supervisor/log/cueadmin.err.log
stdout_logfile_maxbytes=2MB
stderr_logfile_maxbytes=2MB
user=root
priority=999
numprocs=1
process_name=%(program_name)s_%(process_num)02d
```

| 字段 | 含义 |
|---|---|
| `command` | 启动命令（3.4 上面那条） |
| **`directory`** | **进程的工作目录** —— 必须填 `backend/`，理由见下方 ⚠️ |
| `autorestart=true` | 进程挂了自动拉起 |
| `startsecs=3` | 存活超过 3 秒才算启动成功 |
| `startretries=3` | 启动失败重试 3 次 |
| `stdout_logfile` / `stderr_logfile` | 输出重定向到文件 |
| `user=root` | 运行身份 |
| `numprocs=1` | supervisor 管 **1 个进程** |

> ⚠️ **`numprocs=1` 和 gunicorn 的 `-w 2` 不冲突，它们管的是两层。**
> supervisor 管的是 **gunicorn 主进程**（1 个），
> gunicorn 自己再 fork 出 **2 个 uvicorn worker**（子进程）。
> 所以 `ps aux | grep gunicorn` 会看到 1 主 + 2 子，这是对的。

> ⚠️ **`directory` 填错会导致日志消失。**
> `app/core/logger.py` 里写的是 `logger.add("logs/app.log", ...)` —— **相对路径**，
> 相对的就是这个 `directory`。填对是 `backend/logs/app.log`，填错日志就跑到别的地方去了。

### 3.5 配 nginx 反向代理 + SSL

**不需要先「添加站点」。** 宝塔「网站」页面有独立的**「反向代理」**入口，直接填：

| 项 | 填什么 |
|---|---|
| 代理域名 | `cue-api.<root>` |
| 目标 URL | `http://127.0.0.1:8000` |

这样就直接生成 vhost 配置文件，站点列表里不会多出一个站点。

> **生成的配置里会有一行 `root /www/wwwroot/cue-api.<root>;`** —— 那是宝塔的模板固定带的，
> 但**这个目录不会被用到**（所有请求都被 `location ^~ /` 转给后端了，nginx 根本不去读文件系统）。
> 目录存不存在都无所谓，无视即可。

**然后申请 SSL 证书**（宝塔「SSL → Let's Encrypt → 一键申请」）。

生成的配置大致长这样（`<root>` 相关的部分要换成你自己的）：

```nginx
server {
    listen 80;
    listen 443 ssl;
    http2 on;
    server_name cue-api.<root>;

    ssl_certificate     /www/server/panel/vhost/cert/cue-api.<root>/fullchain.pem;
    ssl_certificate_key /www/server/panel/vhost/cert/cue-api.<root>/privkey.pem;

    location ^~ / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
    }
}
```

> **`location ^~ /` 吃所有路径** —— 因为这个域名**只服务后端**，不需要按路径分流。这正是它和"前端域名下转发 /api"的区别。

宝塔实际生成的配置比上面这个长，会多出这些东西（**都不用管，也别删**）：

| 多出来的 | 作用 |
|---|---|
| `ssl_protocols` / `ssl_ciphers` / `ssl_session_cache` | SSL 参数 |
| `add_header Strict-Transport-Security` | HSTS |
| `#WEBSOCKET-SUPPORT` 块 | websocket 支持 |
| `proxy_connect_timeout` / `proxy_read_timeout 600s` | 超时（长任务、大文件下载用得上） |
| `location ~* (\.env.*\|README\.md\|...)` 等 | 敏感文件/目录拦截 |
| `access_log` / `error_log` | 日志 |

> ⚠️ **最后那条敏感文件拦截，在 `location ^~ /` 存在时其实不会生效。**
> nginx 的规则是：`^~` 前缀一旦命中就**跳过所有正则 location**，而那两条拦截规则是正则（`~*`）。
>
> 影响不大 —— 所有请求都被转发给后端了，nginx 压根不去读文件系统，那两条规则拦不拦结果一样。
> 但**以后自己写 nginx 时，`^~` 和正则 location 混用要当心**。


### 3.6 验证后端

```bash
# 本机
curl http://127.0.0.1:8000/health

# 走域名（此时 DNS 还没配，用 --resolve 临时指定）
curl --resolve cue-api.<root>:443:<服务器IP> https://cue-api.<root>/health
```

期望返回：

```json
{"status": "ok", "database": "ok", "redis": "ok"}
```

**任何一个不是 `ok`，先别往下走。**

## 四、第二步：域名解析

在阿里云「云解析 DNS」加两条记录：

| 主机记录 | 记录类型 | 记录值 | 说明 |
|---|---|---|---|
| `cue-admin` | **CNAME** | ESA 给的接入地址 | 例：`cue-admin.<root>.a1.initba.com` |
| `cue-api` | **A** | 服务器公网 IP | 例：`120.79.212.244` |

> ESA 的接入地址在「ESA 控制台 → 站点 → 域名 → 添加域名」时给出。**先做第四步的 ESA 配置，它会告诉你填什么。**

`cue-api` 用 A 记录直连服务器，**不经过 ESA** —— 避免 API 响应被 CDN 缓存导致用户数据串号。

## 五、第三步：前端构建 + 上 OSS

### 5.1 填后端地址

编辑 `frontend/.env.production`：

```bash
VITE_API_BASE_URL = https://cue-api.<root>
```

> ⚠️ **这个值会被写死进构建产物。** 换后端要重新构建。
>
> **必须是 `https://`** —— 前端是 HTTPS 时请求 HTTP 接口，浏览器会以 Mixed Content 拦掉（连预检都不会发）。

### 5.2 构建

```bash
cd frontend
pnpm install
pnpm build
```

产物在 `frontend/dist/`。

> 构建前可以先 `pnpm typecheck`。`VITE_API_BASE_URL` 在类型里是**必填**的，漏配会在这一步报错 —— 比运行时静默请求相对路径好。

### 5.3 上传 OSS

阿里云「OSS 控制台 → Bucket → 文件管理 → 上传」，把 `dist/` 里的**内容**（不是 dist 目录本身）传到 Bucket 根目录。

传完应该是：

```
index.html
assets/
  index-xxxxx.js
  index-xxxxx.css
version
...
```

### 5.4 绑定自定义域名

「Bucket → 传输管理 → 域名管理 → 绑定域名」：

| 项 | 填什么 |
|---|---|
| 域名 | `cue-admin.<root>` |
| 证书 | 用阿里云免费证书或已有证书 |

绑好后 OSS 会提示添加 CNAME 记录 —— 就是第四步里那条。

> **`index.html` 的缓存策略要单独设。** 它是入口文件，名字不带 hash，被缓存住的话前端更新后用户拿到的还是旧的。建议给 `index.html` 设「不缓存」，`assets/` 下的带 hash 文件设长期缓存。

## 六、第四步：ESA 配置

**ESA 控制台 → 站点 → 添加站点**，绑定根域名 `<root>`。

### 6.1 添加域名

「域名 → 添加域名」，填 `cue-admin.<root>`，源站选 **OSS**（选你那个 Bucket）。

ESA 会给一个 CNAME 接入地址，**填回第四步的 DNS 记录**。

### 6.2 配缓存规则

「规则 → 缓存规则 → 新增规则」：

| 项 | 值 |
|---|---|
| 规则名称 | `网站页面-cue-admin.<root>` |
| 匹配字段 | **主机名** |
| 匹配值 | `cue-admin.<root>` |
| 缓存策略 | HTML 不缓存；`assets/*` 长期缓存 |

### 6.3 配内容优化（压缩）

「规则 → 内容优化规则 → 文件压缩」，同样按主机名匹配 `cue-admin.<root>`，开启 gzip / brotli。

> **不要在 ESA 上给 `cue-api.<root>` 配任何东西** —— 它压根不走 ESA（DNS 是 A 记录直连服务器）。

## 七、第五步：验收清单

按顺序过一遍，每步都通过再往下：

| # | 检查 | 命令 / 操作 | 期望 |
|---|---|---|---|
| 1 | 后端进程 | `ps aux \| grep gunicorn` | 能看到 worker 进程 |
| 2 | 后端本机 | `curl 127.0.0.1:8000/health` | `{"status":"ok",...}` |
| 3 | 后端域名 | 浏览器打开 `https://cue-api.<root>/health` | 同上，且证书有效 |
| 4 | 接口文档 | `https://cue-api.<root>/docs` | 能看到 Swagger |
| 5 | DNS（前端） | `nslookup cue-admin.<root>` | 解析到 ESA 地址 |
| 6 | DNS（后端） | `nslookup cue-api.<root>` | 解析到服务器 IP |
| 7 | 前端页面 | 浏览器打开 `https://cue-admin.<root>` | 看到登录页 |
| 8 | **登录** | `admin` / 改过的密码 | 能进后台，侧边栏有菜单 |
| 9 | **跨域** | F12 → Network → 看登录请求 | 状态 200，**没有 CORS 报错** |
| 10 | 多环境 | 若有 staging | 指向对应后端，互不串 |

**第 8 步是整个部署的分水岭** —— 能登录说明前端找到了后端、CORS 通了、后端连上了数据库和 Redis。

## 八、常见问题

### 登录时控制台报 CORS 错误

```
Access to XMLHttpRequest at 'https://cue-api.xxx/login' from origin
'https://cue-admin.xxx' has been blocked by CORS policy
```

**排查顺序：**

1. **先看 Network 里那条请求的真实状态码。** 如果返回 500 或 502，那 CORS 报错是假象 —— 真正的问题是后端挂了或反代配错，响应里没带 CORS 头而已。
2. 后端能正常返回时，检查 `app/main.py` 的 `CORSMiddleware`。当前是 `allow_origins=["*"]` + `allow_credentials=False`，**这个组合本身是合法且够用的**。
3. 如果改成了 `allow_origins=["https://cue-admin.xxx"]`，确认域名**一字不差**（含协议、不含结尾斜杠）。

> ⚠️ `allow_origins=["*"]` 和 `allow_credentials=True` **不能同时用** —— 浏览器规范禁止。如果强制这么配，Starlette 会回显请求方的 Origin，等于**任何网站都被放行还允许带 cookie**。

### 控制台报 Mixed Content

```
Mixed Content: The page at 'https://cue-admin.xxx' was loaded over HTTPS,
but requested an insecure resource 'http://cue-api.xxx'
```

`.env.production` 里的地址写成了 `http://`。改成 `https://` 重新构建。

### 接口返回 404

前端请求打到了**前端域名**上：

- 检查 `.env.production` 的 `VITE_API_BASE_URL` 有没有填
- 检查构建产物里是不是真写进去了：`grep -r "cue-api" dist/`
- 填完要**重新 `pnpm build`**（改 `.env` 不会影响已构建的产物）

### 前端更新后用户看到的还是旧页面

`index.html` 被缓存了。去 OSS / ESA 把 `index.html` 的缓存策略改成**不缓存**。

### 后端启动就报错退出

`validate_secrets()` 拦住了。看日志：

```
RuntimeError: 缺少必要配置: DATABASE_URL, JWT_SECRET
```

或者 `DATABASE_URL` 格式无效。检查 `.env` 文件位置（要在 `backend/` 下）和内容。

### 改了表结构怎么更新

```bash
cd backend
alembic revision --autogenerate -m "描述改动"
alembic upgrade head
```

> **不要重新跑 `python seed.py`** —— 它只负责首次建表，不改已有表结构。
>
> **绝不手写 `op.alter_column` 改列定义**（历史事故：丢过全库主键的 `AUTO_INCREMENT`）。

## 九、附：日常运维

### 日志在哪

**三个地方，查问题时按顺序看：**

| 日志 | 路径 | 内容 |
|---|---|---|
| **应用日志** | `/www/wwwroot/cueadmin/backend/logs/app.log` | Loguru 全量（DEBUG 级），50MB 切割，留 30 天 |
| **进程输出** | `/www/server/panel/plugin/supervisor/log/cueadmin.err.log` | stderr，生产只记 WARNING+ |
| **nginx** | `/www/wwwlogs/cue-api.<root>.log` / `.error.log` | HTTP 层（谁在什么时候调了什么） |

```bash
# 应用日志 —— 排查业务问题看这个
tail -f /www/wwwroot/cueadmin/backend/logs/app.log

# 进程输出 —— 后端起不来时看这个（启动报错在这里）
tail -f /www/server/panel/plugin/supervisor/log/cueadmin.err.log

# nginx 访问日志 —— 排查跨域/404/502 看这个
tail -f /www/wwwlogs/cue-api.<root>.log
```

> **查问题顺序：先看进程日志（起没起来）→ 再看应用日志（业务报什么错）→ 最后看 nginx（请求到没到）。**
